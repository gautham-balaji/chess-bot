**Repository state:** commit `31eb674`, clean tree. C1 and C2 accepted; regression

Every claim below is tagged **VERIFIED** (reproduced from artifacts in this

## A. Executive summary

The training pipeline **is** reproducible in its data-selection stage and **is not**
reproducible in its model-fitting stage. `games.csv` exists on disk, and the exact
10,000-position training sample was regenerated byte-faithfully during this audit.

The audit found **four defects in the training data that no previous phase
identified**, all VERIFIED by replaying the notebook's own code:

1. **Mate labels are corrupted.** 209 of 10,000 positions (2.09%) return
   `{'type': 'mate'}`, and the notebook reads `['value']` without ever checking
   `['type']`. A "mate in 1" was stored as the label `1`; **a position already
   checkmated was stored as `0`** — i.e. "perfectly equal". The most decisive
   positions in the dataset carry near-zero targets.
2. **The `np.clip(val, -1500, 1500)` guard is dead code.** Its comment says "clip
   outlier mate scores", but **zero** of the 10,000 raw values exceeded ±1500,
   because mate values are small distances, not large centipawn numbers.
3. **The "all positions at ply 20" claim is false.** Only **91.5%** (9,155) are at
   ply 20. 845 positions (8.4%) are shorter — down to **ply 1** — because
   `board_after_fullmove` truncates at `tokens[:20]` and many sampled games are
   shorter than 20 plies.
4. **Labels use two different sign conventions.** The `stockfish` package defaults
   to `turn_perspective=True`, so labels are **side-to-move relative**. 9,554
   positions are White to move (label = White-positive) but **446 are Black to
   move** (label = Black-positive = White-**negative**). ~4.5% of labels are
   sign-inverted relative to the rest.

The audit also found **evaluation leakage**: **6 of the 52** `phase0_52` evaluation
positions (11.5%) appear as **exact FEN matches** in the training set. The
`extended` 160-position suite has **zero** overlap.

**The most important design finding (§L):** adding a side-to-move plane while
keeping the current labels would make the engine *worse*, not better. The CNN would
learn to reproduce the side-to-move-relative sign flip, and the engine consumes its
output as a White-positive score. **C6 cannot be a representation-only change** —
the labels must be normalised to a single perspective first, which makes it a
change to the training target and not merely to the input encoding.

**Recommendation:** do not run a representation-only C6 experiment. Fix the label
pipeline first (mate handling + perspective), and treat the label fix and the
representation change as two separately measured arms.

### D.1 Mate labels are corrupted (VERIFIED)

Replaying the pipeline over all 10,000 positions:

```
eval TYPE distribution : {'cp': 9791, 'mate': 209}
label range after clip : min=-1141 max=1369 mean=38.4
values hitting ±1500   : 0
```

`get_evaluation()` returns `{"type": "cp" | "mate", "value": int}`. **The notebook
never reads `["type"]`.** For mate positions `value` is the mate *distance*, so:

| Raw value | Meaning | Label actually stored |
|---:|---|---:|
| `1` | mate in 1 | **1** |
| `0` | **checkmate already on the board** | **0** |

Five sampled examples, all checkmated or mate-in-1 positions, were stored with
labels of 0 or 1 — indistinguishable from a dead-equal position. **2.09% of the
training set teaches the model that forced mates are equal.**

This is a plausible contributor to the mate failures the Phase 3 harness measured
(4 `missed_forced_mate`, 3–4 `engine_move_allows_forced_mate` per suite), though
this audit does **not** establish causation.

### D.2 Labels are order-dependent (VERIFIED)

`Stockfish.set_fen_position` **does not** send `ucinewgame` — the package docstring
states the parameter "has been removed, and this function will no longer send the
`ucinewgame` command". One process is reused for all 10,000 queries, so the
transposition table persists across the entire run in `df.sample` order.

Phase 3 measured this exact effect on the reference side: with a shared hash, the
same Stockfish at the same fixed depth produced **different best moves on 19 of 52
positions** depending on call sequence. The labels carry the same dependency.
Regenerating them requires the identical binary **and** the identical iteration
order.

### D.3 Two sign conventions in one label set (VERIFIED)

Labels are side-to-move relative, and 446 positions are Black to move. Those 446
labels are therefore **sign-inverted** with respect to the other 9,554. The CNN
cannot tell them apart (no side-to-move plane), so they act as ~4.5% label noise
under the dominant White-positive convention.

## E. Current CNN input representation

`board_to_planes` in `engine.py` and `board_to_tensor` in notebook cell 14 were
compared over 160 positions: **0 mismatches — the training and inference encoders
are identical.** (**VERIFIED**)

Shape `(8, 8, 12)`, dtype `float32`, values strictly `{0.0, 1.0}` (binary

## J. C6 representation options

Three candidate encodings for each feature, judged against the existing design
(8×8 spatial, binary, absolute orientation, no normalisation).

### 1. Side to move

| Option | Encoding | Assessment |
|---|---|---|
| **1a. Full 8×8 plane** | One extra plane, all 64 cells `1.0` if White to move else `0.0` | Consistent with existing spatial binary design; costs 64 floats; immediately visible to the first Conv2D. **Recommended** |
| 1b. Scalar side-input | Separate `Input(1)` concatenated after `Flatten` | Cheaper, but changes the model from `Sequential` to functional and breaks the single-tensor contract `engine.board_to_planes` relies on |
| 1c. Orientation flip | Mirror the board so the side to move is always "White" | Standard in strong engines, but it **changes the meaning of every existing plane** and would invalidate the entire existing label set. Far beyond a representation fix |

### 2. Castling rights

| Option | Encoding | Assessment |
|---|---|---|
| **2a. Four full planes** | One plane each for `K`, `Q`, `k`, `q`, constant 0/1 | Consistent; 4 extra planes; trivially derived from `board.has_kingside_castling_rights(color)` etc. **Recommended** |
| 2b. Four marked squares | Set a single cell (e.g. the rook's home square) per right | Sparser and arguably more spatial, but a single cell among 64 is a very weak signal after BatchNorm |
| 2c. One packed plane | One plane holding a 0–15 bitmask value | Breaks the strict binary invariant; introduces an ordinal scale the network must decode |

### 3. En passant

| Option | Encoding | Assessment |
|---|---|---|
| **3a. One plane, single square set** | Plane of zeros with `1.0` at `board.ep_square` | Genuinely spatial — the location matters, unlike side-to-move. Empty plane when `ep_square is None`. **Recommended** |
| 3b. One constant plane | All-ones if an e.p. capture is available | Discards *where*, which is the informative part |
| 3c. Omit | — | Defensible on frequency grounds, but it is one plane and completes the FEN-critical set |

## K. Recommended C6 representation

**`(8, 8, 18)` — the existing 12 planes unchanged, plus 6 appended.**

| Plane | Meaning | Values | Spatial? | Derivation |
|---:|---|---|---|---|
| 0–11 | **unchanged** (see §E) | 0/1 | yes | unchanged |
| 12 | Side to move is White | all-`1.0` or all-`0.0` | constant | `board.turn == chess.WHITE` |
| 13 | White kingside castling | constant 0/1 | constant | `board.has_kingside_castling_rights(chess.WHITE)` |
| 14 | White queenside castling | constant 0/1 | constant | `board.has_queenside_castling_rights(chess.WHITE)` |
| 15 | Black kingside castling | constant 0/1 | constant | `board.has_kingside_castling_rights(chess.BLACK)` |
| 16 | Black queenside castling | constant 0/1 | constant | `board.has_queenside_castling_rights(chess.BLACK)` |
| 17 | En-passant target square | single cell `1.0`, else all-zero | **spatial** | `board.ep_square`, mapped with the existing `row = 7 - sq//8, col = sq%8` |

**Rationale:** planes are **appended**, never reordered, so planes 0–11 keep their
current meaning and the change is purely additive. Everything stays binary `{0,1}`
`float32` with absolute orientation and no normalisation, matching the existing
design. All six are available for **every** legal position — `ep_square` is simply
`None` most of the time, giving an all-zero plane.

**Availability: VERIFIED** — every field is a plain attribute of `chess.Board`, with
no dependency on move history or external data.

**Cost:** input grows 12 → 18 channels. Only the first `Conv2D` kernel changes
shape (`3×3×12×64` → `3×3×18×64`), adding ~3,456 parameters to a 2.36 M-parameter
model (**+0.15%**). Every downstream layer is unchanged.

**This invalidates the existing `cnn_model.keras`** — an 18-channel model cannot
load 12-channel weights. C6 is necessarily a retrain, not a patch.

## L. Label / perspective implications — the critical finding

**Question:** does adding side-to-move information merely complete the
representation, or does the training target itself have to change?

**Answer: the target must change. A representation-only C6 would make the engine
worse.** Reasoning, traced through the actual code:

**Training semantics (VERIFIED).** Labels are **side-to-move relative**
(`turn_perspective=True`). 9,554 positions are White to move, 446 are Black to move.
So the label set is *mostly* White-positive with ~4.5% sign-inverted entries.

**What the current model learned (INFERRED, but tightly constrained).** The CNN has
no side-to-move plane, so it physically cannot fit a turn-dependent function. Given
95.5% White-to-move data it necessarily converges on a **White-positive evaluation
of a piece placement**, treating the 446 Black-relative labels as noise. This is
consistent with the measured behaviour: +342 cp with White a queen up, −486 cp with
Black a queen up, and identical output for the same placement with either side to
move.

**Inference semantics (VERIFIED, Phase 4B).** `rerank_moves` scores candidates on a
**White-positive** scale — `material_balance` is White-minus-Black and all Ridge
coefficients are positive — and the sort direction encodes the side. The engine
therefore *requires* the CNN to be White-positive.

**What happens if you add side-to-move but keep the labels.** The model gains the
ability to condition on the turn, and the labels tell it that Black-to-move
positions should be scored Black-positive. It will learn exactly that — because it
finally can. Its output then **flips sign for Black-to-move positions**, while
`rerank_moves` still reads it as White-positive.

This matters acutely because of where the engine calls it: **every candidate
evaluation in `rerank_moves` is of a *post-move* position, where the side to move is
the opponent.** When the engine plays Black (the only case `app.py` allows), every
candidate is a White-to-move position — fine. But the 1-ply lookahead evaluates
positions one ply deeper, which are Black-to-move. A turn-aware, turn-relative model
would invert the sign on exactly those. That is a regression mechanism, not a
hypothetical.

**Therefore C6 has two separable components:**

| Component | Change | Necessity |
|---|---|---|
| **L1. Label normalisation** | Make every label White-positive: `Stockfish(..., turn_perspective=False)`, or negate when `board.turn == chess.BLACK` | **Prerequisite.** Also fixes the 446 inverted labels that are currently noise |
| **L2. Representation** | Add the 6 planes of §K | The actual C6 change |

**L1 is a change to the training target and must be measured on its own.** It is
also independently justified: it removes ~4.5% label noise regardless of whether L2
happens.

A third, separate defect surfaced by this audit:

| **L0. Mate-label repair** | Read `['type']`; map `mate` to a signed large magnitude (e.g. ±(2000 − 10·|mate_in|)), and handle `mate == 0` (checkmate on the board) explicitly | Independent of C6, and arguably higher value — it currently teaches the model that forced mates are equal |

## M. Controlled retraining experiment design

**Not executed.** The Phase 3 evaluator remains the sole oracle; no new benchmark.

### Arms

Because the audit found three separable defects, a single "C6 vs current" comparison
would confound them. Minimum useful design:

| Arm | Labels | Representation | Isolates |
|---|---|---|---|
| **A0 — control** | as-is (side-to-move relative, mate corrupted) | 12 planes | Retraining noise vs the shipped model |
| **A1 — mate fix** | L0 applied | 12 planes | Effect of correct mate labels |
| **A2 — perspective fix** | L0 + L1 | 12 planes | Effect of consistent White-positive labels |
| **A3 — C6** | L0 + L1 | **18 planes** | Effect of the added representation |

A0 is essential: without it, any A3-vs-shipped difference cannot be separated from
run-to-run variance, since the shipped model's seed is unrecoverable (§H).

### Held constant across all arms

Same `games.csv` (sha256 pinned) · same `df.sample(10000, random_state=42)` · same
derived positions · same `train_test_split(test_size=0.2, random_state=42)` · same
`validation_split=0.1` · same architecture apart from the first Conv2D input depth ·
same loss, optimizer, LR schedule, batch size, epoch cap and callbacks · same
Stockfish binary, depth 8, **Threads=1, Hash=16, Clear Hash per position** (the
Phase 3 configuration, which also makes labels order-independent) · same evaluation
suites and `evaluation/evaluate.py`.

### Seeds

The shipped model has no seed, so exact reproduction is impossible. Instead:
**train every arm with ≥3 seeds** (`keras.utils.set_random_seed(s)` for
`s ∈ {0, 1, 2}`) and compare **distributions**, not single runs. Without this, a
difference of a few percentage points in top-1 agreement is uninterpretable — Phase
4A and 4B both showed how easily a real code change produces zero measurable effect.

### Measurements

**Model-level** (per arm, per seed): final training loss, final validation loss,
epochs to early stop, best epoch, **Pearson r vs Stockfish on the held-out 2,000**
(comparable to the recorded 0.708), MAE and RMSE in centipawns, and Pearson computed
**separately on the mate subset** to test L0 directly.

**Engine-level** (per arm, via the unmodified Phase 3 harness, on **both**
`phase0_52` and `extended`): legality · top-1 Stockfish agreement · top-3
containment · mean / median / p95 / max regret · blunder rate >300 cp · regret
coverage · mate statuses (`missed_forced_mate`, `engine_move_allows_forced_mate`) ·
Spearman mean/median · White vs Black · opening / middlegame / endgame breakdown.

**Diff-level** (via the existing `evaluation/compare_runs.py`): number of selected
moves changed · per-position regret deltas · improved vs worsened vs unchanged
counts.

### Pre-registered success criteria

State these **before** running, to avoid post-hoc rationalisation:

- **Primary:** mean regret on `extended` (n=152 defined) improves by ≥20 cp, and
  median regret does not worsen.
- **Secondary:** blunder rate >300 cp falls; `missed_forced_mate` +
  `engine_move_allows_forced_mate` falls (this is the direct L0 hypothesis).
- **Guardrail:** legality stays 100%; no metric regresses materially.
- **Null result is a valid outcome** and must be reported as such — as in 4A and 4B.

### Cost estimate

Label regeneration ~1–2 min per label variant (10,000 positions at ~175/s,
VERIFIED from the retained notebook output). Training: 55 epochs × ~4 s ≈ 4 min per
run. Evaluation: ~2.5 min (`phase0_52`) + ~9 min (`extended`) per arm. For 4 arms ×
3 seeds ≈ **3–4 hours** of compute, dominated by evaluation.

## N. Fairness / leakage considerations

### Evaluation/training overlap — leakage confirmed (VERIFIED)

Exact-FEN comparison of the regenerated 10,000-position training set against both
evaluation suites:

| Suite | n | Exact-FEN overlap | Placement-only overlap |
|---|---:|---:|---:|
| `phase0_52` | 52 | **6 (11.5%)** | 6 |
| `extended` | 160 | **0** | 0 |

The six are `OP02`, `OP03`, `OP04`, `OP05`, `OP06`, `OP17` — all very early opening
positions at plies 1–3. They entered training because 845 sampled games are shorter
than 20 plies, so `board_after_fullmove` truncated to their opening moves.

**Implication:** `phase0_52` metrics are mildly contaminated — the CNN saw those six
positions with Stockfish labels during training. The effect is small (6/52) and
these are shallow opening positions where labels are near-zero anyway, but it
**cannot be described as an independent evaluation**.

**`extended` (n=160) has zero overlap and should be treated as the primary
evaluation suite for C6.** `phase0_52` remains valuable for continuity with Phases
0/3/4A/4B, and its overlap must be stated whenever it is quoted.

## Q. Recommended next step

**Do not run a representation-only C6 experiment.** It would be confounded by
corrupted mate labels, contaminated by two label sign conventions, and — per §L —
could actively regress the engine by making the CNN turn-relative while the engine
reads it as White-positive.

Recommended order:

1. **C6-prep (one phase, no retraining):** extract the dataset and label generation
   from the notebook into `training/build_dataset.py`, with a pinned Stockfish
   configuration (Threads=1, Hash=16, Clear Hash per position), an explicit mate
   policy, `turn_perspective=False`, FEN-level deduplication, and a committed
   metadata manifest. Output an inspectable labelled dataset artifact. **This makes
   every later arm reproducible and is prerequisite to all of them.**

2. **Run arm A0 (control) first.** Retrain on the current pipeline with 3 seeds and
   measure the spread. This establishes the noise floor. Phases 4A and 4B both
   showed that a real correctness fix can produce exactly zero measurable change —
   without a noise floor, a C6 result cannot be interpreted.

3. **Then A1 → A2 → A3**, measuring each with the unmodified Phase 3 harness on
   `extended` (primary) and `phase0_52` (continuity, overlap disclosed).

4. **Expect, and be willing to report, a null result.** The honest prior from this
   project is that correctness fixes here have not moved measured quality. The
   difference this time is that L0/L1 change the *training signal* rather than a
   term contributing <1% of the score — so there is a plausible mechanism for a real
   effect, particularly on the mate statuses. That is a hypothesis, not a prediction.

A reasonable smaller alternative, if time is limited: **do step 1 and arm A1 only.**
The mate-label repair is cheap, independently justified, has a concrete measurable
target (the 8 mate failures across the two suites), and does not require touching the
representation at all.
